HelioNova: one design system for every renewable-energy product

HelioNova builds products for two very different audiences: families watching their rooftop solar, and engineers running wind and solar parks. I designed the shared design system behind both, with foundations, 28 accessible components and copy-paste HTML that works in any framework.

Overview

Project overview

HelioNova’s products had grown separately. The customer app, the installer portal and the operations console each had their own buttons, greens and chart styles, and the same "energy generated" number looked different in every one.

The goal was one system that feels warm and simple for homeowners, is precise enough for grid engineers, and is easy for any team to adopt without a framework migration.

The challenge

Problem statement and pain points

HelioNova had three products built by three teams over four years: the customer app (homeowners tracking rooftop solar and savings), the installer portal (surveys, quotes and installs) and the operations console (engineers monitoring wind and solar parks). Each grew its own UI. A UI audit of 140 screens found the same patterns rebuilt again and again, and the inconsistency was now costing time, trust and accessibility.

Problem statement

Designers and developers across HelioNova have no shared foundations or components. Every team recreates buttons, tables and metric cards in its own framework, so the same energy data looks and behaves differently in each product. This slows delivery, confuses customers who use more than one product, and leaves accessibility gaps that block public-sector and utility contracts.

Inconsistent UI

The same "energy generated" figure used three fonts, two units (kWh vs MWh) and different colours for "up".

Who feels it: homeowners and operators comparing numbers

02

Slow, duplicated delivery

Each new feature rebuilt its own modal, table and metric card. Roughly a third of front-end effort went on UI that already existed elsewhere.

Who feels it: designers, developers, product managers

03

Accessibility gaps

Status shown by colour alone, missing focus states, and a dark mode that failed WCAG contrast. This blocked tenders that require AA.

Who feels it: users with low vision, sales and compliance

04

Mixed tech stacks

React, Angular and server-rendered pages meant a React-only library would leave two of three teams behind.

Who feels it: engineering leads planning migrations

05

No single source of truth

Design files, code and brand guidelines disagreed. Nobody could say which version of a component was "correct".

Who feels it: new joiners, QA, brand team

06

Weak trust in the data

Customers saw different savings figures in the app and in emails, which drove support calls and doubts about the product.

Who feels it: customers, support team

How might we

How might we give every HelioNova team one shared language for building energy products, one that works in any framework, meets WCAG 2.1 AA in light and dark, and makes energy numbers look the same everywhere?

Approach

My approach

  1. UI audit: screenshotted every screen across the three products and grouped duplicates by pattern.
  2. Foundations first: colour, type, spacing and icons, defined as tokens before any component was drawn.
  3. Component inventory: prioritised the 28 components that covered most of the audited screens.
  4. Plain HTML and CSS: every component ships as copy-paste markup, so it works with any stack.
  5. Documentation as product: a searchable site with live examples, code and accessibility notes for each component.

Principles

Design principles

01

Naturally clear

Calm surfaces and a nature-inspired palette, so the data is what stands out.

02

Numbers you can trust

One way to show kWh, MW and savings, with units and change always labelled.

03

Accessible by default

AA contrast in both themes, visible focus, and never colour alone for status.

04

Works anywhere

Plain HTML and CSS with tokens, so any team can adopt it today.

Foundations

Colour: five scales from sunlight, canopy and sky

Each scale has ten steps. Components never use raw hex values; they use semantic tokens such as --hn-primary and --hn-danger, which switch automatically in dark mode.

Accessibility

WCAG 2.1 AA in light and dark

Contrast

  • Text ≥ 4.5:1 in both themes
  • UI borders ≥ 3:1
  • Dark theme tuned separately

Keyboard & focus

  • Every control reachable by Tab
  • Visible Sky-blue focus ring
  • Modals and drawers trap focus

Meaning

  • Status uses icon + text, not colour
  • Tooltips work on focus, not just hover
  • Reduced-motion respected

Governance

Keeping the system alive

  1. Versioning: semantic versions (v1.0 today) with a changelog for every release.
  2. Contribution: teams propose components through a short template: problem, examples, accessibility notes.
  3. Office hours: a weekly session for designers and developers to review new patterns together.

Closing

Key takeaways

  • Foundations before components: agreeing tokens first meant components rarely needed rework.
  • Plain HTML wins adoption: no framework lock-in meant every team could start the same week.
  • Domain components matter: the energy stat card made the system feel built for HelioNova, not borrowed.
  • Docs are the product: live examples and copyable code did more for adoption than any presentation.
