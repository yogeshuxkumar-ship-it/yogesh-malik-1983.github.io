Stratos AI: one console for a fleet of AI agents

A redesign of Stratos AI, an observability and governance console for enterprise AI agents. Teams run dozens of agents across models, frameworks and environments, and need to see what is failing, what it costs and why, in seconds, at a desk or on call.

Overview

Project overview

Enterprises now run AI agents built on different models (Gemini, GPT, Claude, Llama), frameworks (LangGraph, LangChain, CrewAI, Bedrock) and MCP tool servers, across dev, test and production. Each one has its own latency, error rate and token bill.

Without one place to watch them, teams found problems through angry users or a surprise invoice. Stratos AI brings every agent into one console; my redesign made that console about triage, not just data.

Before
  • Every metric had the same visual weight
  • Alerts hidden in a separate tab
  • Filters spread across pages
  • No path from an agent to its traces
  • Desktop only
→
After
  • An alert banner leads, with severity counts
  • KPIs grouped by health, spend and trend
  • The same filter bar on every list
  • Fleet → agent → trace in two clicks
  • A mobile layout for on-call triage

The challenge

Problem statement

  1. Signal lost in noise: as fleets grew, the console showed lots of data but no priorities.
  2. Slow root cause: moving from a failing agent to the exact prompt meant several screens and copy-pasted IDs.
  3. Hidden cost: token spend per agent was hard to compare, so budgets surprised teams.
  4. Away from the desk: on-call engineers had no usable view on their phones.

How might we help an AI-ops team spot, understand and fix an agent problem in under a minute, wherever they are?

Approach

My approach

  1. Audit of the existing console: what each screen showed, and what teams actually looked for first.
  2. Task analysis of the most common jobs: check health, find a failing agent, debug a trace, compare spend.
  3. Information architecture built around zoom levels, from fleet down to a single prompt.
  4. Greyscale wireframes for desktop and mobile, then a high-fidelity interactive prototype.
  5. Reusable patterns for filters, tables, status chips and expanding rows.

Principles

Design principles applied

Six principles guided every screen, on desktop and on mobile.

PriorityTriage before analytics

Applied: Alerts lead every view; charts give context after.

Impact: Problems are seen first, not found by accident.

Visual hierarchyCalm density

Applied: Light surface, neutral palette and one blue accent, so status colours stand out.

Impact: Dense data stays readable.

Same filters everywhereConsistency

Applied: Segmented controls and dropdowns behave the same on Agents and Traces.

Impact: Learn once, use everywhere.

AccessibilityNever colour-only

Applied: Every status has a text label as well as a colour.

Impact: WCAG-friendly and fast to scan.

Cognitive loadProgressive disclosure

Applied: Agent details expand inline instead of opening new pages.

Impact: Context is never lost.

Context of useMobile for on-call

Applied: Cards, a bottom tab bar and large touch targets for paged engineers.

Impact: Triage is possible away from a desk.

Closing

Key takeaways

  • In operations tools, order matters more than amount: the same data, ordered by urgency, changes how fast people act.
  • Consistency is speed: identical filter patterns mean people learn them once.
  • Mobile is a different job, not a smaller screen: on call, people need to triage, not analyse.
  • AI products still need classic ops UX: agents fail like any other service, so proven SRE patterns apply.
